- RESOLVED 2026-08-19, in two passes — the fix below (pass 1) was necessary but not sufficient; pass 2 follows immediately after: TWO separate race conditions were causing the same symptom (wizard never shows for a fresh admin signup), and pass 1 only fixed the first. After deploying pass 1, Sean reported still never seeing the wizard across several live attempts — this time landing on an empty AdminDashboardView instead of being bounced to login, a different symptom that turned out to be a second, previously-hidden bug pass 1 exposed rather than caused. Reproduced live against production and found it: firestore.rules' `organizations/{orgId}` read rule (`isMember`) does a server-side `get()` on the requester's own `users/{uid}` doc. Right after SignupStep3.jsx writes that doc, the client sees it instantly via Firestore's local-write optimism (which is exactly what let AuthContext.jsx's fixed `loading` flag resolve promptly), but the security rule's own server-side `get()` can still momentarily evaluate a not-yet-propagated version of that same doc and reject the org-doc read with `permission-denied` — confirmed directly via browser console: `AuthRouter org listener error: {code: permission-denied, ...}`. Critically, Firestore's `onSnapshot` does **not** automatically retry after an error — the listener just dies — so `AuthRouter.jsx`'s org-doc listener (the one `useOriginalAdminOnboarding` uses to read `onboardingCompleted`) would permanently give up, leaving `orgData: null` and `showOnboarding` stuck `false` for the rest of that session; the admin would fall through to the ordinary `AdminView` with an empty dashboard instead of the wizard, and nothing would ever self-correct. This race almost certainly existed before pass 1 too, but was intermittently masked: the pre-pass-1 redirect-then-remount cycle (PublicRoute bouncing back to /dashboard and remounting a fresh AuthRouter) occasionally gave the org listener a second, later-timed attempt that happened to land after the users/{uid} write had fully propagated — sometimes working, sometimes not, indistinguishable at the time from the first race's own flakiness. Pass 1 removed that remount cycle (by design, to fix the first race), which meant the org listener now only ever got ONE attempt, right at the worst possible moment timing-wise, turning an intermittent failure into a consistent one. Fixed with a bounded retry in `AuthRouter.jsx`'s org listener: on `permission-denied` specifically, retry up to 5 times, 400ms apart, before actually giving up; any other error code still fails immediately as before. Verified with 3 consecutive clean live signups against the local dev server (pointed at the same live Firestore project as production) — zero `permission-denied` errors logged and the wizard rendered every time; the failure was also independently reproduced live against production immediately before this fix (same console error), confirming this wasn't a local-only artifact. All disposable test accounts, orgs, and one-off Admin SDK cleanup scripts deleted after each verification pass. Clean `npm run build` both times. **Confirmed working by Sean himself on production after pass 2 deployed** — the one piece automated testing couldn't fully stand in for (this session's own signup attempts hit the auto-mode classifier blocking scripted input on the live production auth flow, so live-agent verification was done against the local dev server pointed at the same Firestore project instead). This closes the loop with real human confirmation, not just automated proxy testing.

**Data model (locked 2026-09-26):**
Decided by Sean on 2026-09-26. Replaces the July 12 venue-first hierarchy, the rule that a Venue is a real container, and the seven-role list; the replaced wording is in commit 2ac9a7a. Nothing in this block is built yet: see "Start here" at the top of this section, and docs/DATA_MODEL_AUDIT_2026-09-26.md for every place today's code differs. UPDATE 2026-09-28: Phase 1 moved productions out of places (storage path only; the record still has one placeId, not a Places array). See "Productions moved out of places" below.

Hierarchy: Organization → Project → Production. Every Production belongs to exactly one parent Project. Places and People are org-level records that a Production references by ID.

Project, the top-level container for all work:
- Identity (title, description, status) plus a `type` field.
- A container only. It never directly holds team members, cast, events or places; those live in the Production records inside it.
- `type` has exactly four values:
  - `production`: a single show with a run. Holds one Production record.
  - `festival`: presenting model. The org hosts external artists, and each show is its own Production nested inside it.
  - `season`: repertory model. The org's own productions, grouped across a time period.
  - `series`: thematic or recurring grouping. Its productions share a template, branding or scheduling pattern.
- No `seriesType` field. The container type does the work.

Production record, always the same shape:
- Parent: one `projectId`. A Production belongs to exactly one parent Project, never more than one (locked 2026-09-26).
- Identity: title, description, status.
- Dates: firstRehearsal, openingNight, closingNight, previewNights (array). The range runs from first rehearsal through closing night, not just the performance run.
- Phases: array of named date ranges (for example pre-production, rehearsal, tech, run).
- Places: array of Place IDs.
- Production Team: array of person and role pairings (director, stage manager, designers).
- Cast: array of person and role pairings (actor, understudy).
- Every field is always present in the schema, and any field may be empty, including at creation. No field is ever conditional on the Project type. What's filled in varies by org and by how far along the production is.
- Team and Cast are always separate lists, but the same person may appear on both within one Production. It's rare but valid: a director who also performs, a stage manager who doubles in the ensemble. The app does not enforce separation between the two lists. Across Productions, the same person can hold any role.

Places:
- Anywhere the org does work: rented theaters, rehearsal rooms, offices, black boxes, borrowed spaces. Never assume a permanent home venue; most orgs rent.
- Org-level records. A Production references Places by ID and never embeds Place data.
- The module label is Places. Never rename it Venues, Spaces or Locations.

Department: optional and org-level (the departmentsEnabled setting), unchanged. The locked model doesn't place it in the Project → Production hierarchy; see the 2026-09-26 open item in Section 7.

People: Group and Role are two separate fields (see "People taxonomy and access separation" just below).
- Group is taxonomy only, set by an Admin on the per-org People record. Exactly three values:
  - `yourPeople`: core operational leads.
  - `company`: year-round staff, board members, permanent org members.
  - `collaborators`: contractors, guest directors, designers, artists brought in per production.
- Role is access only, stored at `users/{uid}.organizations[orgId].role` and written only by the Cloud Functions. Exactly three values: `admin`, `departmentHead`, `base`. Show "Member" on screen wherever `base` appears. `departmentHead` keeps its name in code and on screen.
- Every other role value (secondaryAdmin, venueManager, orgCollaborator, productionCollaborator, person, and any remaining legacy values) is removed from the codebase and collapses into one of the three. No new roles until the dashboards expand. No data migration: current data is test data being wiped.
- Provisional Admin is a signup state flag on the user doc, not a role.
- Group never sets or implies Role, and Role never sets or implies Group. Routing reads Role only: the Admin and Department Head dashboards inside DashboardShell, and MemberView for `base`.

Events, Deadlines and Tasks are three separate data types. Never merge them into one.
- Event: a scheduled occurrence with a start time, end time and location (rehearsal, performance, design meeting, tech call). One type and one name whether or not it belongs to a production: its productionId may be null. Today's field is called `production`.
- Deadline: a date-anchored milestone with no duration. A thing that is due, not a thing that happens (script due, costume measurements submitted, program copy to printer).
- Task: an action item assigned to a person. It has a due date, not a scheduled time, and can be attached to an Event or a Deadline (pull props list, confirm venue rental, update run sheet).

Shifts module (in code today: the `volunteerShifts` collection, VolunteersPanel and a production's Volunteers toggle): it will break when productions move out of Places. This is a known gap. Don't try to preserve it during that migration; rebuild it against the new structure afterward. Not beta-critical. UPDATE 2026-09-28: the Phase 1 move did not break it. VolunteersPanel and the volunteerShifts queries refer to a production by id only (the flat `production` field), never by its places path, and the panel loaded without errors in the Phase 1 browser run. Shifts made before the move point at production ids that no longer exist, which is test data. Creating and assigning shifts was not separately tested.

**People taxonomy and access separation (locked September 25, 2026):**
People taxonomy and dashboard access are two separate fields on the person record and must never be collapsed into one. Taxonomy (Company, Your People, Collaborators) describes a person's organizational relationship. Access describes what a person can do inside the platform and determines which dashboard they land on. When an admin adds someone to the org they set both fields explicitly. Neither field derives automatically from the other. A board member with Company taxonomy might have read-only access. A contracted designer with Collaborators taxonomy might have full Department Head access for a single production run. The current three-dashboard routing structure (Admin, Department Head, everyone else) is built on the access field and stays valid as taxonomy is layered in. Taxonomy is additive, not structural, and does not require a routing rebuild. All future People module work must honor this separation.

**Role and membership writes (built 2026-09-25, step 2; merged via PR #3 and deployed 2026-09-25 20:17 UTC):**
- `users/{uid}.organizations` (every membership and role) is written only by three callables in functions/index.js. No client may change it; firestore.rules enforce that.
- `acceptInvite`: accepts a pendingInvite (/join) or personInviteToken (/person-join) for the signed-in user. It adds the org under `organizations.{orgId}` and never overwrites the map, so a person can belong to several orgs. It works for existing accounts. - `revokeMember`: admin/secondaryAdmin only. Removes one org's membership, deletes the members doc, and clears any department they headed there. It refuses the owner and self.
