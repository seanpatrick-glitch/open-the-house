The live site's own Hosting deploy was collateral damage of this bug, not just a red CI badge.

This is a Google Cloud project setting, not a per-machine one, so it should have fixed CI too — confirmed locally afterward (`firebase deploy --only firestore:rules,firestore:indexes,functions,hosting:main` exited 0, new Hosting release landed). **FIREBASE_TOKEN retired, migrated to FIREBASE_SERVICE_ACCOUNT (2026-08-18, later same-day session):**

No `--token` flag remains in either file. firebase-deploy.yml's existing Hosting-isolated structure (Deploy Hosting first and alone, Deploy Firestore rules/indexes/functions second and isolated) was preserved exactly — only the auth mechanism changed. - Confirmed via a live CI run: Deploy Hosting succeeds cleanly under the new auth (proves the service account and the auth action are correctly wired) — but Deploy Firestore rules, indexes, and functions failed with the exact same exit code 2 as every run under the old FIREBASE_TOKEN. **RESOLVED (2026-08-18, same day):** Sean pulled the actual expanded log from the GitHub Actions UI and pasted the real error, which this session could never have seen on its own: `⚠ functions: Couldn't find firebase-functions package in your source code. Have you run 'npm install'?` followed by `functions: Loading and analyzing source code for codebase default to determine what to deploy` then `Error: An unexpected error has occurred.` The actual root cause had nothing to do with auth or Node version: `firebase deploy` loads `functions/index.js` locally to introspect which functions to deploy, which requires `firebase-functions`/`firebase-admin` to already be installed — but the workflow's "Install dependencies" step only ever ran `npm ci` at the repo root, which never touches `functions/`'s own separate `package.json`. Every local manual deploy this whole investigation relied on for "confirms locally, fails in CI" comparisons had actually been misleading: it worked locally only because `functions/node_modules` already existed there from an earlier, unrelated local `npm install`, not because anything about the deploy command itself was CI-incompatible. CI does a full fresh checkout every run, so that directory never existed there at all, on any of the runs tested. Fixed with one added step — `npm ci` with `working-directory: functions` — placed after the Firebase CLI install and before both deploy steps. Confirmed two ways: (1) every step in the next CI run succeeded, including both "Deploy Hosting" and "Deploy Firestore rules, indexes, and functions"; (2) directly queried the live Firebase Rules API and Hosting API afterward and confirmed both a new Firestore ruleset and a new Hosting release landed with timestamps matching that exact run, not just trusting the green checkmark. The service-account auth migration and the Node-24 pin both remain in place — neither was the fix, but neither was wrong to have either, and reverting either now would be pure churn with no benefit.
- **Net result:** firebase-deploy.yml is now fully working end to end — Hosting, Firestore rules, Firestore indexes, and Cloud Functions all deploy automatically on every push to main, authenticated via the modern FIREBASE_SERVICE_ACCOUNT method, with Hosting isolated from the other three so a future failure in any of them can never again cost the live site its own deploy. The original org-creation rule bug (see above) is the direct beneficiary: any future rules change like it will now deploy automatically within minutes of being pushed, with no manual `firebase deploy` step required and no way for it to silently sit undeployed the way this one did since May.
