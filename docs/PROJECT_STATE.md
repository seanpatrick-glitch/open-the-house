## SECTION 3: DATA ARCHITECTURE

**Hierarchy (locked):**
Organization → Department (optional) → Venue → Production

**Department:** Optional tier. Activated by larger orgs (fringe festivals, multi-department organizations). Invisible to smaller orgs. Can be activated later without a rebuild.

**Venue:** Real container, not a tag. People can be assigned to a production, a venue, or both.

**Role types:**
- Admin (org-wide, title configurable)
- Secondary Admin
- Department Head
- Org Collaborator (oversight, board/executive level)
- Venue Manager (optional, site-specific)
- Production Collaborator (scoped to one production)
- Person (configurable label: volunteer, artist, staff, technician, etc.)

RESOLVED July 12 in App Architecture session: these seven are the confirmed canonical role values (admin, secondaryAdmin, departmentHead, orgCollaborator, venueManager, productionCollaborator, person). Provisional Admin is not an eighth role — it is a state flag (`provisionalAdmin: boolean`, `accountState: provisional | confirmed`) on the user document, cleared once ownership is confirmed or the signup user's real role is set.

**People coordination module:**
Three-layer intake schema. Universal fields always present. Toggleable common fields admin turns on or off. Admin-defined custom fields. Supported types: text, date, select, multiselect, checkbox groups, file upload.

**Planning Timeline architecture (spec locked):**
- View switcher: three views (timeline, calendar, list), org default plus per-person override
- Recurring timelines: template-based using offsetDays from anchor date
- Task visibility: visibleToAll boolean
- Cross-department access requests: restricted to Department Heads only
- Org Collaborators: view-only with clarification flag capability
- Notifications (Phase 1): in-app plus email, three triggers (overdue, due-soon, handoff-ready)
- Production-timeline relationship: Scenario C, built in two stages

**Messaging, department timelines, task handoff, and multi-person assignment architecture (spec locked July 23):**
- Messaging: threads, messages, and broadcasts collections, denormalized read state, two Cloud Functions, two composite indexes. RESOLVED 2026-08-17: broadcast fan-out for more than 250 recipients now correctly chunked (see Section 2 and Section 8).
- Department timelines: level enum, departmentId, and promotedToOrg fields on tasks; denormalized task counts on department document via Cloud Function; three composite indexes; DH-scoped write rules. DH departmentId read path needs confirmation before rules deploy (open).
- Task handoff: currentAssigneeUid and handoffPending on task document, handoffs subcollection, append-only history subcollection, atomic batch write on acceptance.
- Multi-person task assignment: primaryAssigneeUid replaces assignedTo, contributorUids array, append-only notes subcollection, contributor composite index, notification routing split between primary and contributors.
- Build prerequisites: two migration scripts (assignedTo to primaryAssigneeUid, level field backfill on existing tasks), three Cloud Functions total, Firebase Functions initialization as Step 0. Full 26-step build sequence produced; order is Area 2 (department timelines), Area 4 (multi-person assignment), Area 3 (task handoff), Area 1 (messaging).

**Events architecture (2026-08-16):**
- Top-level, org-scoped `events` collection, structured like `tasks`: scope org|department (department scope requires departmentId), optional date/time/location fields, DH write access scoped to their own department via the same departments.departmentHeadUid lookup pattern as tasks.
- Recurrence is a simple repeat rule only (weekly or monthly, with an end date) — no arbitrary patterns, no specific weekday-of-month rules, no per-occurrence edits or exceptions. Explicitly out of scope by design.
- Recurring events are materialized as real documents at save time, one per occurrence, all sharing a generated recurrenceGroupId — not resolved as virtual/dynamic occurrences at read time. Capped at 104 generated occurrences (weekly for 2 years).
- Write and read paths both built (2026-08-16): CreateEventForm.jsx (write, prior session) plus CalendarGrid.jsx and GanttView.jsx display (this session), both reading the same `events` collection queried once in TimelineView.jsx and filtered by the existing department/org pills via event.scope and event.departmentId. No dedicated events-only list/detail route exists — display is via the Timeline's Calendar and Gantt views only, matching how tasks are also surfaced. See Section 2 and Section 8.
