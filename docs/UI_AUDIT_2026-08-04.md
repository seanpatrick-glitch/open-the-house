## SECTION 3 — New Issues Found This Pass

None of these existed in the original report. Two are small implementation gaps in the recent fixes themselves; the rest are deeper structural findings from tracing the actual data model (see Section 4 for the full picture).

1. **Should-fix — the quick-action navigation mechanism is now internally inconsistent.** Two different patterns coexist for what should be one concept: `DepartmentsView.jsx` uses a normal passed-in `onNavigate` prop, while `AdminDashboardView.jsx` and `DHDashboardView.jsx` use a global `window.dispatchEvent('navigate', ...)` caught by a listener in `DashboardShell.jsx`. Root cause: `DashboardShell.jsx` doesn't pass `onNavigate`/`navState` to the Home section at all, so those two dashboards had no choice but to invent the event-based workaround. Both paths work correctly today — this isn't broken, it's fragile. It's exactly the "half-migrated, two competing patterns" risk the remediation plan called out as a reason to do this refactor as one coordinated pass — worth a follow-up cleanup so the next quick action added doesn't have to guess which pattern to copy.

2. **Should-fix — a new toast can spam under sustained failure.** The "mark thread as read" fix in `VolunteerView.jsx` sits inside an `onSnapshot` callback rather than a one-time effect (contrast with the equivalent, correctly-scoped fix in `MessagingView.jsx`). If that particular write keeps failing, every subsequent change to the thread re-triggers the snapshot, re-attempts the write, and re-fires the error toast — a real, if narrow, duplicate-toast risk introduced by the Tier 5.3 fix itself.

3. **Should-fix, and a genuinely new finding — the Department cards' "people count" is structurally always zero.** `DepartmentsView.jsx` computes it by filtering each person's `assignments[]` array for an entry where `type === 'department'` — but `AssignmentsPanel.jsx` (the only place assignments are ever created) only ever writes `type: 'production'` or `type: 'place'`. There is no UI path anywhere in the app that creates a `'department'`-type assignment. This isn't a data-population gap that'll fix itself once Sean starts assigning people — the write path for it doesn't exist. Every department card, in every org, will show "0 people" forever, regardless of how many people are actually in that department. See Section 4, Tie Gap 1, for the full picture.

4. **Should-fix, new finding — Tasks are never actually linked to a Production**, despite the schema having a field for it. `CreateTaskForm.jsx` writes `production: null` on every single task, with no UI control to set it to anything else. `TimelineView.jsx` even has a `{task.production && <p>Production linked</p>}` badge sitting in the code, ready to display a link that can never exist. See Section 4, Tie Gap 3.

## SECTION 4 — Feature Ties: gaps between modules that should connect but don't

This is the part of the app that doesn't show up as a single broken button — it shows up as data that quietly never reaches the place it was supposed to go. Walking through the product's own declared architecture (Organization → Department (optional) → Venue → Production, plus People/PersonTypes, Tasks, Messaging, Check-in) against what the code actually wires together:

### Tie Gap 1 — "Which department is this person in?" has three different, disconnected answers, and the one a real UI number depends on has no writer at all

There are three separate places in the codebase that could answer "which department does this person belong to," and none of them talk to each other:

- `personType.departmentId` — exists in the schema, hardcoded to `null` at creation (`CreatePersonTypeForm.jsx`), and never editable anywhere, including after the Tier 1 fix (that fix wired up the sibling field `departmentHeadId` on the same document, but not this one).
- `member.departmentId` — correctly set for staff (Department Head, Secondary Admin, etc.) via the role-based invite flow, but hardcoded to `null` forever for Person-class members (artists, volunteers) in `PersonJoinPage.jsx`.
- `person.assignments[].type === 'department'` — the exact thing `DepartmentsView.jsx`'s people-count card depends on, but `AssignmentsPanel.jsx` never creates an assignment of this type; only `'production'` and `'place'` exist as options.

**Practical effect:** the Departments page will show "0 people" on every card, permanently, in every org — a visible, confusing number that undermines confidence in a screen Sean will look at constantly during Phase 0 setup and beyond.

### Tie Gap 2 — "Message the department" can't reach the people who are actually in it

`BroadcastForm.jsx`'s department-scoped broadcast logic is completely correct code — it filters recipients by `member.departmentId` exactly as it should. But because Person-class members never get a `departmentId` on their member doc (Tie Gap 1, second bullet), a Department Head who clicks "Message the department" will only ever reach *other staff* assigned to that department — never the artists, volunteers, or techs who are the actual audience for that message. The feature works; the data that would make it useful is never populated. This is a real functional gap in one of the app's core messaging features, hiding behind code that looks (and is) correct in isolation.

### Tie Gap 3 — Tasks have no connection to a specific Production

The task schema has a `production` field (`models/timeline.js`), `CreateTaskForm.jsx` writes it on every task — always as `null`, with no UI to set it otherwise — and `TimelineView.jsx` has a "Production linked" badge that can consequently never render. For an org running one show at a time this doesn't bite yet, but Places People's own target market (fringe festivals, multi-show seasons) is exactly the case where this matters: there's currently no way to see or filter "which tasks belong to this specific production" at all, at either the org or department level. This is a deeper version of the already-known "production scope not wired into timeline generation" item — it's not that scope-specific *behavior* is missing, it's that the basic task-to-production link was never built in the first place.

### Tie Gap 4 — Places/Productions and Departments are entirely parallel, unconnected silos

The locked data hierarchy (Section 3 of PROJECT_STATE.md) is explicitly "Organization → Department (optional) → Venue → Production" — Departments are supposed to sit above Venues. Nothing in the actual code reflects that nesting: `CreatePlaceForm.jsx` and `CreateProductionForm.jsx` have zero department-related fields. A venue or production can't currently be scoped to a department at all. Worth resolving before any "festival scope" work begins, since festival scope (per PROJECT_STATE) is specifically about multi-department, multi-venue behavior that depends on this link existing.

### Tie Gap 5 — Department Head identity exists as two unlinked fields, with no cross-check

`department.departmentHeadUid` (real, working, the department-level concept) and `personType.departmentHeadId` (also real and working now, the permission-scoping concept Tier 1 fixed) are two separate fields that happen to mean almost the same thing in plain English but have no relationship to each other in code. Nothing warns Sean if he assigns different people to each during Phase 0 setup — no validation, no suggested default, no visible link between the two screens where each gets set (Departments vs. Settings → Person Types). Low urgency, but worth a note since it's exactly the kind of quiet inconsistency that produces a support question during beta ("why can't my DH see the department she's supposed to head?").

### Tie Gap 6 — Check-in is production-aware; Tasks are not

`CheckInView.jsx` has a working production/date picker — it already knows how to scope itself to a specific show. Tasks, per Tie Gap 3, don't have this at all. Two modules that both conceptually need "which show is this for" solved the problem differently (one correctly, one not at all), which is worth flagging as an inconsistency in addition to the standalone Tie Gap 3 finding.

### Tie Gap 7 (naming, not a bug) — "Assignment" means two unrelated things

`Person.assignments[]` (roster/scheduling — "this artist is assigned to this production") and `Task.primaryAssigneeUid`/`contributorUids` (task ownership — "this task is assigned to this person") are completely separate concepts that happen to share the word "assignment." No code confusion was found, but it's worth flagging as a vocabulary collision — both because it could confuse Sean during a future spec session, and because Tie Gap 1's missing `'department'` assignment type is easy to conflate with "assign someone to the Wardrobe department" (a staffing/roster idea) when the actual working mechanism for staff department membership is the entirely separate `member.departmentId` field. These are two different things wearing the same name.
