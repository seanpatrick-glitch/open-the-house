# Places People! — UI, Gap & Adoption-Friction Audit
> Date: 2026-08-02
> Scope: Static code audit (read-only). Live browser/credential sign-in testing intentionally deferred per standing preference — see "Methodology" note below.
> Auditor: Claude Code

## Methodology note

This audit was conducted entirely by reading source code, Firestore security rules, and git history — no live browser sign-in testing was performed as part of the original static pass. The task brief for this audit was framed around tracing code paths (AuthRouter, views, forms) rather than interactive testing, consistent with the standing preference to save live browser/credential testing for a dedicated session.

**Update, 2026-08-02 (same day, later session):** Sean ran the Tier 0 manual verification from the companion remediation plan against a disposable test org with a real Department Head test account. Both of the plan's Tier 0 targets are now **live-verified, not just static-analysis findings**:
- **The Department Head people-write bug is confirmed live.** As the DH test account, People → Add Person → Save fails to save the person, consistently, every attempt — matching the predicted cause exactly (the `firestore.rules` `resource.data.typeId`/`request.resource.data.typeId` bug, compounded by the missing `personTypes.departmentHeadId` assignment UI).
- **The passwordless-lockout bug is confirmed live.** Signing out of the newly-created test account left no way back in, matching the predicted cause exactly (no password ever set at invite acceptance, no recovery path on the sign-in screen).

Both findings below are now empirically confirmed in addition to being verified by direct code reading.

## SECTION A — Findings by Role

### A1. Admin / Secondary Admin

Both route through `AuthRouter.jsx` to `AdminView` → `DashboardShell`, the full nav shell (Home, Messages, Timeline, Departments [gated by `org.departmentsEnabled`], Places, Productions, Check-In, Collaborators, People, Settings). Secondary Admin has no visible distinction in the UI from Admin (PROJECT_STATE claims "Secondary Admin mirrors Admin minus billing tile" — there is no billing tile anywhere in the app to remove, so this is currently a no-op distinction; not a bug, just a claim that has nothing to differentiate yet).

**AdminDashboardView.jsx** — genuinely implements all four claimed states (Planning / Final Countdown / Live / Postmortem) with distinct live Firestore queries per state and respects `dashboardStateOverride`. This is real, not a stub.
- **should-fix**: Quick Action buttons (`Add a timeline task`, `Invite a team member`, `Message the org`, lines ~271-285) fire a `window.dispatchEvent(new CustomEvent('navigate', ...))` rather than any passed prop. This works only because `DashboardShell.jsx` happens to have a matching `window.addEventListener('navigate', ...)` — but it's a global-event pattern with no direct wiring, the same shape PROJECT_STATE itself flagged as "a dead window.dispatchEvent('navigate') call that had never actually worked" for VolunteerView's old Messages button. It works today only because DashboardShell listens; worth a comment or safer prop-based wiring since it's easy to break silently.
- **should-fix**: Every quick action opens a *section*, never a form — "Add a timeline task" lands on the Timeline list, not `CreateTaskForm` pre-opened. See Adoption Friction section — this is a systemic pattern, not unique to one dashboard.
- **should-fix**: Load errors (`catch (err) { console.error(...) }`, line 85) are silent — a failed org/production read leaves the dashboard stuck in default Planning state with zero explanation.
- **polish**: Loading state is plain text ("Loading dashboard..."), not a skeleton — causes a layout jump into the real content.
- Brand voice: em dashes in visible header copy — `AdminDashboardView.jsx:211` (`${daysToOpen} days — ${prodName}`), `:213` (`Tonight — ${prodName}`), `:306` (`Tomorrow — overdue or not started`).

**HomeView.jsx** (`src/components/dashboard/HomeView.jsx`) — **confirmed dead code**, imported in `DashboardShell.jsx` but never returned by any branch of `SectionContent` (Home always resolves to `AdminDashboardView` or `DHDashboardView`). It's also full of hardcoded placeholder data (`PLACEHOLDER_PRODUCTIONS`, fake "The Tempest" rows) with unused Firestore imports. Harmless since unreachable, but should be deleted — it's exactly the kind of leftover PROJECT_STATE already flagged for `Navbar.jsx`/`SectionNotes.jsx`/`UserManagement.jsx` and never caught this one.

**DepartmentsView.jsx** — task-completion and people-count per card are real and live (matches claim). Empty state is good ("No departments yet. Add your first department to start organizing your team.").
- **CONFIRMED TRUE**: "Department card tap sets level pill but does not filter to the specific department." `DepartmentsView.jsx` passes `{ departmentFilter: dept.id }` on tap; `TimelineView.jsx` only uses that to flip a generic `levelFilter` to `'department'` — the actual filter predicate never checks `task.departmentId`. Every department card currently opens the identical "all department-level tasks, from every department" view, which will visibly confuse a DH who taps her own department expecting to see only her tasks.
- `DepartmentDetail.jsx` is dead code (imported nowhere) — its own placeholder cards ("Places/People/Timeline — Coming soon.") never render to any real user, but the file exists as orphaned weight with a real-looking department-head-email lookup nobody triggers.
- Stats loading has no try/catch around the `Promise.all` — a failed query throws uncaught inside an `onSnapshot` callback with zero fallback.
- Brand voice: `CreateDepartmentForm.jsx:181` — "Loading users…" (the literal banned word "users"); `:191` — "— Assign later —" (em dash as decorative punctuation in a visible `<option>`).

**PlacesView.jsx / CreatePlaceForm.jsx** — list + Add a Place + detail view genuinely built, good empty states ("No places yet...", "No productions at this place yet...").
- **CONFIRMED TRUE**: "Places detail fields incomplete/unspecced." The place document schema is `{ name, orgId, createdAt, createdBy }` only — no address, capacity, contact info, or notes anywhere in the create form or the schema. A "venue" in this app is currently a named folder, nothing more. This matches PROJECT_STATE's own note that places detail fields need a Feature Roadmap spec — confirmed still true, not yet done.
- No user-visible error state on load failures (console-only).

**ProductionsView.jsx / CreateProductionForm.jsx / ProductionDashboard.jsx** — solid empty-state handling (distinct messaging for "no places yet" vs "no productions yet," with a CTA in the places-empty case). Active Modules toggle grid has real optimistic-update-with-revert behavior — a genuinely well-built pattern.
- **CONFIRMED TRUE**: "Production scope field captured but not wired into timeline generation." `PRODUCTION_SCOPE` is required at creation and stored, but no code anywhere in `src/` branches on it for timeline/template generation. `models/productions.js` documents this gap itself. Not a beta blocker per PROJECT_STATE (festival/season scope work is explicitly non-blocking), but confirmed still open.
- **should-fix**: `ProductionDashboard.jsx` still shows a literal "Production dashboard content coming soon." placeholder below the modules grid (lines ~185-187) — a real, user-facing stub.
- Brand voice: multiple em/en-dash date-range and empty-value renders across `ProductionsView.jsx` (`:37`, `:85`, `:274`) and `ProductionDashboard.jsx` (`:45`, `:60`, `:140`); `CreateProductionForm.jsx:129` has an em dash in visible placeholder copy ("e.g. Show, Event, Festival — defaults to Production if left blank").

**SettingsView.jsx** — Departments toggle, Active Production selector, Dashboard State Override, Signup Links, Person Types list are all real and wired.
- **CONFIRMED — and this is the root cause of the People-module blocker (see Section B)**: there is no UI anywhere — not in SettingsView, not in CreatePersonTypeForm, not anywhere in `src/` — that ever sets a real uid on a personType document's `departmentHeadId` field. `CreatePersonTypeForm.jsx:47` hardcodes `departmentHeadId: null` at creation and nothing ever edits it afterward. This is a distinct field from the department-level `departmentHeadUid` (which *is* settable, via `CreateDepartmentForm.jsx` at department-creation time, or via the new invite-acceptance flow) — the two are easy to conflate but the Firestore rules that gate Department Head writes to `people` records depend specifically on the personType-level field, which no UI ever populates.
- Every write path in this file (`handleToggle`, `handleSetActiveProd`, `handleSetOverride`, `fetchSettings`, `loadProductions`) fails silently to the user on error — console-only.
- **should-fix**: Signup-link "Copy" button gives no success/failure feedback (no toast).

## SECTION B — The Tempest Trace (Department Head's first task)

This is the literal beta test happening in the next couple weeks, and the single most important trace in this audit.

**The path, as designed:**
1. Sean invites Tempest via `InviteCollaborator.jsx`, selecting role "Department Head" and a department from the picker (built Aug 1). This writes a `pendingInvites` doc and calls `sendSignInLinkToEmail`.
2. Tempest opens the email, clicks the sign-in link.
3. Link lands on `/join`, handled by `JoinPage.jsx`. `isSignInWithEmailLink` succeeds; the code checks `localStorage.getItem('emailForSignIn')`.
4. **Friction point 1 (high severity, see Section D):** that localStorage key was set on *Sean's* browser when *he* sent the invite (`InviteCollaborator.jsx:151`), not on Tempest's device. On her phone, this will always be empty, so `JoinPage.jsx:33` falls through to a raw, unstyled **`window.prompt('Please enter your email to confirm your identity.')`** — a native browser dialog with zero Places People branding, zero explanation of why she's being asked, indistinguishable in appearance from a phishing prompt to someone with no context. This is the very first thing she sees after clicking a legitimate email link. **This is not an isolated one-off** — the identical `window.prompt()` pattern exists at `PersonJoinPage.jsx:28` for the Person-class join flow, meaning every artist Tempest later invites to self-signup will hit this same jarring dialog too. Fixing it once fixes both paths.
5. She types her email correctly (best case) → sign-in succeeds → `JoinPage` reads `orgId`/`inviteId` from the URL (these *are* correctly embedded in the link, so this part survives cross-device fine) → looks up the `pendingInvites` doc → shows an "Almost there" card with an optional display-name field → she clicks Continue.
6. Batch write creates her `users` doc and `organizations/{orgId}/members` doc with `role: 'departmentHead'`, `departmentId` from the invite; if it's a DH invite, also writes `departmentHeadUid` onto the department document. This part is solid and correctly wired (verified against `firestore.rules` lines 95-101).
7. `navigate('/dashboard')` → `AuthRouter` → `departmentHead` → `AdminView` → `DashboardShell` → Home resolves to `DHDashboardView`.
8. **Friction point 2 (medium severity):** `DHDashboardView`'s Planning state shows an "Overdue" section (if any), a "Department Tasks" list or an empty-state card ("No upcoming department tasks."), and two Quick Action buttons — neither of which mentions People, artists, or the roster. There is **no call to action anywhere on this first-landing screen pointing her toward adding her people.** She has to already know, or guess, that the sidebar item labeled "People" — using generic system vocabulary, not "Artists," "Cast," or "Roster," any of which a Fringe festival DH would actually recognize — is where her task lives.
9. She clicks "People" in the sidebar (always visible, not gated). `PeopleView.jsx` loads: if Sean's Phase 0 setup pre-created an "Artist" person type, the list is empty with "No people yet. / Add your first person to get started." and an "Add Person" button, top right.
10. She clicks "Add Person." `CreatePersonForm.jsx` renders inline. If only one person type exists, it auto-selects (nice touch). She fills Name (required), Email, Phone, Emergency Contact, plus whatever custom fields Sean configured for artists, and clicks "Save Person."
11. **This is where it breaks.** `CreatePersonForm.jsx` calls `addDoc(collection(db, 'organizations', orgId, 'people'), {...})`. In `firestore.rules`, the only write rule available to a `departmentHead` on `organizations/{orgId}/people/{personId}` is:
    ```
    allow write: if isDepartmentHead(orgId)
      && get(.../personTypes/$(resource.data.typeId)).data.departmentHeadId == request.auth.uid;
    ```
    Two independent, compounding problems:
    - `resource.data.typeId` references the document as it exists **before** the write. On a Firestore `create`, no such document exists yet, so this clause can never be satisfied — the correct pattern (used elsewhere in the same rules file, e.g. the task-creation rule two blocks above) is `request.resource.data.typeId`. This is a straightforward rules bug, verifiable by direct comparison of the two patterns in the same file.
    - Even if that were fixed, `departmentHeadId` on every personType document is permanently `null` — confirmed by grepping the entire `src/` tree for every write site: `CreatePersonTypeForm.jsx:47` is the only writer, and it hardcodes `null`. No Settings screen, no other form, edits it afterward. So the clause could never be satisfied for any DH, on any org, ever, with the app as currently built.
    - The self-signup `allow create` clause doesn't apply either (it requires `status == 'applied'` and `createdBy == 'self-signup'`; Tempest's manual add writes `status: 'active'` and her own uid).
    
    **Net effect: Tempest's "Save Person" click returns a Firestore permission-denied error.** `CreatePersonForm.jsx`'s catch block shows a generic "Failed to save. Please try again." — no indication of *why*, and retrying changes nothing, because the block is structural, not transient. **If she was invited as Department Head — the exact role this audit was asked to trace, and the role the whole invite-flow rebuild on Aug 1 was built to support — she cannot complete the single task the entire beta exists to validate.**

    **LIVE-VERIFIED, 2026-08-02:** Sean reproduced this exact failure against a real Department Head test account in a disposable test org — People → Add Person → Save fails consistently, every attempt. No longer a static-analysis-only finding.

12. **Compounding factor — this bug may not even be the first thing she hits.** The beta site (`placespeople-beta-testing.web.app`) deploys from the `beta-stable` branch via GitHub Actions, and `beta-stable` is **24 commits behind `main`** as of today, branched on 2026-07-26 before the entire "24-step dashboard and role-based invite flow" build session. That means, unless Sean explicitly merges `main` into `beta-stable` and pushes before beta launch, the live site Tempest actually visits does not yet have: `DHDashboardView`, the rebuilt `CollaboratorView`/`VolunteerView`, `PlacesView`, the Department card enhancements, the display-name field, the production-scope question, and — critically — **the role-based invite flow itself** (the Aug 1 commit `729846c` that lets Sean invite her as Department Head with a department picker in the first place). On the currently-deployed beta site, that invite screen doesn't exist yet, so this entire trace may not even be reachable as described. See Section F for full detail.

**Click/screen count summary (best case, ignoring the two blockers above):** email click → window.prompt (unexplained) → Continue on JoinPage → land on DH dashboard (no CTA) → click People (tribal-knowledge nav guess) → click Add Person → fill form → Save. That's 4 real navigation decisions plus one jarring unbranded system dialog, with zero in-app guidance connecting "artist roster entry" to the word "People" — before even reaching the point where the save silently fails.

13. **Blocker discovered during Tier-0 manual verification (2026-08-02, Sean testing live), not found by the original static pass — and more severe than anything above.** Once Tempest signs out — for any reason: closing her phone browser, tapping the sidebar's "Sign out" button, clearing cache, a new device — **she cannot sign back in, at all, by herself.** Confirmed by reading every possible re-entry path:
    - The invite/join flow (`JoinPage.jsx`, `PersonJoinPage.jsx`) signs a person in using Firebase's *passwordless* email-link method and never asks them to set a password, at any point in either file.
    - The one and only sign-in screen (`Login.jsx`) requires email **and password** — there is no "email me a link instead" option and no "forgot password" link anywhere on it.
    - Her original invite link cannot be reused: Firebase invalidates an email sign-in link after first use, and separately the app's own invite record flips to `status: 'accepted'` after first sign-in and is never looked up again if `status !== 'pending'`.
    - "Create account" (the link on the Login screen) doesn't help — it's for founding a brand-new org, and `SignupStep1.jsx` explicitly catches and reports `auth/email-already-in-use` for an email that already has an account, which hers now does. Dead end.
    - `sendPasswordResetEmail` (Firebase's standard "forgot password" function) is used exactly once anywhere in `src/` — inside `UserManagement.jsx`, the confirmed-dead legacy admin panel, and even there it's an *admin* resetting someone *else's* password, not a self-service option.
    
    **Net effect: every role except the founding Admin (Secondary Admin, Department Head, Org Collaborator, Venue Manager, Production Collaborator, and every Person/artist/volunteer) is one accidental sign-out away from permanent lockout, recoverable only by Sean personally sending them a brand-new invite, every single time.** This directly contradicts the product's core premise ("no one has to ask Sean for help") more completely than any other finding in this audit, and requires no error, no edge case, and no misconfiguration to trigger — it is the designed, working behavior of the passwordless flow as currently built.

**Suggested minimal fixes, in priority order:**
1. Fix the Firestore rule: change `resource.data.typeId` to `request.resource.data.typeId` on the DH people-write clause (or split into an explicit `allow create` using `request.resource.data`, mirroring the tasks-collection pattern).
2. Add the missing UI: a Department Head picker on the Person Type card in `SettingsView.jsx` (or fold it into `CreatePersonTypeForm.jsx`) that writes `departmentHeadId`. Given `CreateDepartmentForm.jsx` already has a working "assign existing member or invite by email" pattern for department-level DH assignment, that same pattern can likely be adapted here directly.
3. Replace or precede the `window.prompt()` in `JoinPage.jsx` with a branded in-app "Confirm your email" screen — same visual shell as the rest of `JoinPage`, so the flow never drops into raw browser chrome.
4. Add one line of forward-pointing copy to `DHDashboardView`'s Planning empty state and/or a dedicated "Add your people" quick action, e.g. next to "Add a department task": an "Add people" button that routes straight to People with Add Person pre-opened.
5. Rename the sidebar "People" nav label per-org if `personType` labels are configured (e.g. show "Artists" instead of generic "People" when the org's primary person type is "Artist") — or at minimum add a one-line subtitle under the People nav item's first visit.
6. Merge `main` into `beta-stable` (or point the beta Hosting deploy at `main`) before launch, and verify the deployed beta site actually reflects current code.
7. Add a "set a password" field to the same "Almost there" step in `JoinPage.jsx`/`PersonJoinPage.jsx` that already captures display name (item 13 above), and add a "Forgot password?" link to `Login.jsx` wired to `sendPasswordResetEmail`. Both reuse patterns already proven elsewhere in this codebase.

## SECTION C — Admin vs. Collaborator comparison

Contrary to what the audit brief expected going in, **CollaboratorView is not meaningfully thinner than its spec** — it matches the July 26 decision ("view-only: production status, people count, admin-elevated flags, one quick action to flag a note for Admin") closely, with real Firestore-backed data throughout, a working flag-submission form, and reasonable empty/loading states. The one gap: Production Collaborator shares this exact same component with no scoping to the specific production they're assigned to (see A5) — that's a spec gap, not an implementation shortfall.

Where Admin and Collaborator genuinely diverge in ways that read as unintentional:
- Admin gets a full-featured dashboard shell with sidebar nav across 9+ sections; Collaborator gets a single scrolling page. This is by design per spec, not a bug, but worth naming since it's a stark visual difference a Collaborator will notice immediately on first login relative to whatever screenshots/demos they may have seen of the Admin side.
- Error handling is *more* silent on the Admin side than Collaborator's — most Admin write paths (Settings, Departments, Timeline) fail to a console-only `console.error`, whereas Collaborator's single write path (flag submission) at least sets `submitting`/disables the button on failure, giving marginally better feedback than several Admin screens.

## SECTION D — Adoption Friction & Self-Explanatory UI

*(Tempest trace covered in full in Section B — this section covers systemic patterns found across the app.)*

1. **Quick actions never open forms, only sections — a repeated pattern, not a one-off.** Confirmed across `AdminDashboardView`, `DHDashboardView`: every "Add a ___" or "Message ___" quick action dispatches a `navigate` event to a section key (`'timeline'`, `'messages'`, `'invite-collaborator'`) with no mechanism anywhere in `TimelineView.jsx` or `MessageView.jsx` to auto-open a create form or a specific thread. A first-time user clicking "Add a timeline task" from the dashboard lands on a list and must find the separate "New Task" button themselves — the quick action saved zero clicks over just using the sidebar. This is worth fixing as one systemic change (thread a `navState`/`action` flag through the same mechanism `TimelineView` already uses for `departmentFilter`) rather than one-off patches.

2. **`window.prompt()` used as real UI in the sign-in flow** — see Section B, Friction Point 1. This is the single highest-impact adoption-friction item in the app: it's the very first interaction after clicking an invite email, on a device with no prior context, and looks exactly like the kind of dialog security-conscious people are trained to distrust.

3. **Generic vocabulary vs. domain language.** The nav item "People" (and section header "Everyone your organization coordinates, in one place") never adapts to what the org actually calls these people — a Fringe festival DH thinks "artists" or "cast," not "people." The person-type label ("Artist") only ever shows up inside the Add Person flow, not in the primary nav. A one-line copy change (surface the primary person-type label in the nav or page header once configured) would remove a real "is this the right place?" hesitation for a first-time user.

4. **No forward-pointing empty states on dashboards.** `DHDashboardView`'s Planning state, when there are zero department tasks, just says "No upcoming department tasks." — it doesn't say what to do about it (add tasks? add people first?). Compare to `PlacesView`'s much better empty state ("No places yet. Add your first venue to get started.") — the pattern exists elsewhere in the app, it's just not applied consistently to the dashboards, which are the highest-traffic first-landing screens.

5. **Two similar-looking, easy-to-confuse concepts**: department-level `departmentHeadUid` (on the department doc, settable via `CreateDepartmentForm`) vs. personType-level `departmentHeadId` (on the personType doc, meant to gate who can write person records of that type, but with literally no UI to set it — see Section B). These look like the same concept from the outside ("the department head") but are two separate fields serving two separate purposes, and only one of them has a UI. This is squarely an internal architecture leak that will confuse Sean himself during Phase 0 setup, not just a hypothetical end user.

6. **CSV import is a genuinely good bulk-add path** (upload → auto-map columns → preview → confirm, with per-row success/fail counts) but it's tucked behind a hover-only dropdown menu on the "Import CSV" button (`PeopleView.jsx`) — hover menus don't exist on touchscreens, so a DH on a phone or tablet cannot discover this path at all; she'd have to know to tap it and hope a touch event fires the same as a hover. Given the audit brief specifically expects manual one-at-a-time entry for the first beta task, this doesn't block Tempest's specific task, but it's a real gap for any DH working from a phone who has a spreadsheet.

7. **Mobile / one-handed usability** — the People roster (`PeopleView.jsx`) renders as a raw 5-column `<table>` with no responsive fallback; on a phone this requires horizontal scrolling to see Status/Account columns, awkward one-handed in a lobby or backstage. `PersonProfileView.jsx`'s field rows use a fixed `w-36` label column that leaves roughly 170px for values on a 375px screen — workable but tight for longer values like emergency-contact strings. By contrast, Check-in (`CheckInView.jsx`, `SelfCheckInPage.jsx`) and the join/signup flows are well-built for mobile — no tables, adequate tap targets, no hover-only affordances. The roster table and profile view are the two screens most worth a mobile pass given how central they are to a DH's actual day-to-day use.

8. **Error messages are uniformly non-actionable.** Nearly every write path across the app (Settings, Departments, Timeline, People, Messaging) reduces any failure — permission-denied, network error, bad query, whatever — to either total silence (console-only) or a generic "Failed to save. Please try again." A user who hits a real permission wall (like the DH people-write bug above) has no way to distinguish "try again, it's transient" from "this will never work, tell your admin," which matters enormously for a self-serve product whose entire premise is "no one has to ask Sean for help."
